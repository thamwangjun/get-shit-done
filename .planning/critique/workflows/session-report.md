# Critique: session-report.md

## Summary

`session-report.md` is a functional workflow that correctly scopes its job to a single, well-defined output (a session report file), uses XML tags to separate phases, and provides clear shell-command snippets to ground the agent in observable data. However, it falls short on several guide fundamentals: the task intent, audience, and quality bar are never stated explicitly; output format is specified only as a Markdown template embedded inside the process steps rather than in a dedicated `<output_format>` block; instructions mix negative-adjacent framing with missing positive equivalents; no persona is assigned despite this being an open-ended, stylistic generation task; and the display-result step relies on emoji and qualitative descriptors where numeric constraints are required. The workflow is coherent enough to produce a usable report, but it would benefit substantially from the structural discipline the guide prescribes.

---

## Strengths

- **Section 16 (Multi-Phase Workflows) — Phase pattern applied correctly.** The workflow decomposes into four named `<step>` phases (`gather_session_data`, `estimate_usage`, `generate_report`, `display_result`) with clear boundaries between them, matching the guide's phase-based cognitive boundary pattern.

- **Section 4 (Formatting and Structure) — XML tags used for step separation.** `<step name="...">` tags are semantically named, giving the model richer signal than prose headers alone (Section 4 Action 2).

- **Section 8 (Context Placement) — Inline shell commands anchor context to live data.** The bash snippets for `git log` and `git diff` follow the spirit of Section 8's runtime context injection pattern, grounding the agent in real observable signals rather than hallucinated assumptions.

- **Section 14 (Constraint Enforcement) — Success criteria enumerated.** The `<success_criteria>` checklist at the end gives the agent a concrete definition of done, consistent with the guide's pattern of explicit constraint specification.

- **Section 10 (Prompt Length and Compression) — The prompt is appropriately lean.** No redundant instructions or repeated context; each step handles one concern cleanly.

## Issues

### Issue 1 — Task intent, audience, and quality bar are absent
**Guide principle:** Section 1 Action 1 and Action 2 — the three task components (what, why, quality bar) and the audience must be explicit.

**What is missing:** The `<purpose>` block states the output type but not who consumes it or what "high-quality" looks like. Is the reader a technical lead, a non-technical stakeholder, or an automated pipeline? What distinguishes a good report from a mediocre one?

**Fix:** Add to the opening of the workflow:
```xml
<audience>
The session report is read by the developer and optionally shared with stakeholders.
Assume technical literacy; avoid explanatory filler. Prioritize actionable signal over completeness theater.
</audience>
<quality_bar>
A high-quality report is scannable in under 60 seconds, contains only factually grounded claims (no fabricated estimates), and surfaces one clear next action or blocker.
</quality_bar>
```

---

### Issue 2 — No `<output_format>` block; format is buried inside process steps
**Guide principle:** Section 7 Action 1 and Section 22 Pattern 3 — output format must be specified completely and upfront, not embedded as an afterthought inside process logic.

**What is missing:** The Markdown template for the report is inside `<step name="generate_report">` rather than in a dedicated `<output_format>` block at the top level. This means the model must parse process logic to find the format specification, and the format cannot be referenced independently.

**Fix:** Extract the report template into a top-level `<output_format>` block placed after `<purpose>` and before `<process>`. Keep the `generate_report` step focused on data collection logic; reference `<output_format>` by name:
```xml
<output_format>
Write a Markdown file to `.planning/reports/`. Required sections and fields:
- Header: Generated timestamp, Project, Milestone
- Session Summary: Duration, Phase Progress, Plans Executed, Commits Made (all numeric)
- Work Performed: Phases Touched, Key Outcomes (bullet list), Decisions Made
- Files Changed: from git diff --stat
- Blockers and Open Items
- Estimated Resource Usage table
Footer: "Generated by /gsd-session-report"
</output_format>
```

---

### Issue 3 — No persona assigned for an open-ended, stylistic generation task
**Guide principle:** Section 6 Action 1 — assign a specific persona for open-ended or stylistic tasks. Section 6 Action 2 — personas must be specific (constraining voice/register), not generic.

**What is missing:** Generating a session report is an open-ended writing task with a defined voice (concise, factual, stakeholder-facing). No persona is set, so the model defaults to generic assistant register, which produces verbose, hedge-filled prose inconsistent with the GSD style.

**Fix:** Add a persona block:
```xml
<persona>
You are a technical project journalist. Write in present tense, active voice.
Omit filler words. Lead every section with the most important signal.
</persona>
```

---

### Issue 4 — Negative and soft-framed instructions not converted to positive equivalents
**Guide principle:** Section 5 Action 1 — convert negative instructions to positive specifications before emitting any prompt.

**What is missing:** The `estimate_usage` step uses "is not directly available" and "exact token counts require API-level instrumentation not available" — these are accurate caveats but they frame the constraint negatively. The display-result step says "if this is the first report, mention..." which is an implicit conditional rather than explicit branching. The `<success_criteria>` uses "filename includes date to prevent overwrites" where "prevent" is negatively framed.

**Fix (examples):**
- "Count of tool calls is not directly available" → "Derive estimates from observable git activity and file operation signals only."
- "filename includes date to prevent overwrites" → "Filename must include YYYYMMDD date prefix to make each report uniquely addressable."
- Replace "If this is the first report, mention..." with a `<scenario>` block (Section 16) making both branches explicit.

---

### Issue 5 — Display-result step uses emoji and qualitative size language; no numeric constraints
**Guide principle:** Section 21 — size constraints must use numeric limits, not qualitative descriptors. Section 5 Action 1 — instructions should use imperative present tense. Guide stance on emoji is to avoid them unless explicitly requested.

**What is missing:** The display template in `<step name="display_result">` uses emoji (`📄`, `💡`) which introduce inconsistency. More critically, no word count or line count cap is set for the terminal display summary, so the model may produce a summary as long as the report itself.

**Fix:** Remove emoji from the instruction template. Add a numeric constraint:
```
Display a summary of at most 6 lines. Each line states one metric as: Label: Value.
```

---

### Issue 6 — Estimation heuristics are stated as facts without flagging them as heuristic
**Guide principle:** Section 2 Action — flag CoT traces and heuristic outputs as indicative, not ground truth.

**What is missing:** The estimation heuristics ("Each commit ≈ 1 plan cycle", "Each plan file ≈ 2,000-5,000 tokens") are reasonable approximations but are presented as definitive conversions, not calibrated estimates. The model may treat them as authoritative and report fabricated numbers without caveat.

**Fix:** Prefix the heuristics section with an explicit framing instruction:
```
These are order-of-magnitude heuristics only. When generating the report, mark all derived
estimates with "(estimated)" and note they are based on activity proxies, not instrumentation.
```

## Recommendations

Prioritized by impact on output quality and consistency.

**1. Add `<audience>`, `<quality_bar>`, and `<output_format>` blocks (Section 1 Actions 1-2; Section 22 Pattern 3)**
These three are the highest-leverage additions. Without a stated quality bar, the model cannot self-evaluate its output. Without a dedicated `<output_format>` block, the report structure is coupled to the process logic and cannot be independently referenced or updated. Implement all three before any other change.

**2. Add a persona scoped to the report's voice (Section 6 Actions 1-2)**
A concise, factual, present-tense persona directly reduces report verbosity and hedging. This is a one-paragraph addition with measurable style impact. The persona should name the register ("technical project journalist", "engineering lead writing a handoff note") not just "expert summarizer."

**3. Replace implicit conditionals with explicit `<scenario>` blocks (Section 16)**
The "if this is the first report" conditional and the absent-STATE.md case are both undeclared branches. Convert each to a named `<scenario condition="...">` block so the model receives deterministic branching instructions rather than inferring them. This prevents silent failures when the expected files do not exist.

**4. Reframe all negatively framed and heuristic instructions as positive specifications (Section 5 Action 1; Section 2)**
Audit every sentence containing "not", "no", "prevent", or "require ... not available." Convert each to a positive equivalent. For the estimation heuristics, add an explicit "(estimated)" labeling instruction so the agent marks derived values rather than asserting them as fact.

**5. Add numeric constraints to the display summary and a `<scope>` exclusion list to the report (Section 21; Section 19)**
Replace the open-ended display template with a hard line-count limit ("at most 6 lines"). Add a `<scope><exclude>` list to the report format specifying what the report should omit (e.g., raw log dumps, speculative future plans, content already in ROADMAP.md) to prevent the agent from padding the report with low-signal content.
