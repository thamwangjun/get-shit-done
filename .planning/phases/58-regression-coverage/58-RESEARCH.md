## Summary

Phase 58 builds a comprehensive regression suite that freezes the intended post-D-08 behavior for the v2.1.0-e milestone. The suite has four components: (1) a static committed JSON golden fixture that proves bare `{claude,codex}` slots resolve to `medium` effort and all MODEL values are unchanged; (2) extended parser fixture coverage; (3) per-runtime omit/translate contract assertions; and (4) a committed antipattern guard.

The key design insight is that Phase 53's existing dynamic golden (`feat-53-config-sites-and-golden.test.cjs`) derives expected values FROM the resolver under test — a resolver that drifts wrong-but-consistently still passes. The Phase 58 static fixture is committed with literal expected values the resolver cannot influence, providing the actual drift lock. Both coexist and guard different failure modes.

The implementation surface is entirely `tests/` and `tests/fixtures/` — no source changes to `bin/lib/` or `bin/install.js`. The new test file follows the `feat-<N>-*.test.cjs` naming convention already used by `feat-53-config-sites-and-golden.test.cjs` and `feat-57-install-translation.test.cjs`.

**Primary recommendation:** Create `tests/feat-58-regression.test.cjs` + `tests/fixtures/golden-effort-snapshot.json` + `scripts/gen-golden-effort-snapshot.mjs` following the atomic-write pattern from `sdk/scripts/gen-project-root.mjs`.

### Q1: Golden Fixture Mechanics (D-01, D-02)

**How feat-53 iterates the matrix:** `feat-53-config-sites-and-golden.test.cjs` lines 244–308 show the exact pattern. It iterates `agents = Object.keys(MODEL_PROFILES)` (33 agents) × `profiles = ['quality', 'balanced', 'budget', 'inherit']`. For each pair it calls `_resolveAgentSlot` + `parseModelEffort` to derive the expected effort from the resolver under test — this is why it cannot catch wrong-but-consistent drift.

**Profile variant keys (verified from live catalog):** [VERIFIED: npm registry]
```javascript

// profiles: 'quality', 'balanced', 'budget', 'adaptive', 'inherit'
// feat-53 uses: 'quality', 'balanced', 'budget', 'inherit' (omits adaptive)
// Phase 58 D-02 says "all profile variants" — confirm whether adaptive is in scope
```
The VALID_PROFILES from model-profiles.cjs are `['quality', 'balanced', 'budget', 'adaptive', 'inherit']`. The feat-53 dynamic test uses only `['quality', 'balanced', 'budget', 'inherit']` (excludes adaptive). The static golden should cover the same 4 profiles used by feat-53, with adaptive as a "Claude's Discretion" call for the planner — it does not materially change coverage since adaptive uses the `adaptiveTierMap`, not static profile slots.

**JSON shape for the static fixture:**
```json
{
  "generated": "2026-06-06",
  "description": "Static post-D-08 golden: agent × profile × runtime",
  "rows": [
    {
      "agent": "gsd-planner",
      "profile": "quality",
      "runtime": "claude",
```

Keying: flat array of rows with `{agent, profile, runtime, expectedModel, expectedEffort}` — enables both deep iteration in the test and diff-readability in review. The `omitContract` array holds one row per non-effort runtime (13 runtimes: all KNOWN_RUNTIMES minus claude and codex).

**Regeneration script location and pattern:** Follow `sdk/scripts/gen-project-root.mjs` exactly:
- ESM `.mjs` (not `.cjs`) since it uses `import { writeFile, rename, unlink } from 'node:fs/promises'`

- Location: `scripts/gen-golden-effort-snapshot.mjs`
- Invoked: `node scripts/gen-golden-effort-snapshot.mjs` or added to package.json as `gen:golden-snapshot`
- The script calls `resolveReasoningEffortInternal` + `resolveModelInternal` from `core.cjs` directly over the matrix

### Q5: RED-before-fix Evidence and Antipattern Guard (TEST-04, D-04)

**Concrete mutation points per assertion class:**

| Assertion class | Mutation to confirm RED |
|----------------|------------------------|
| Golden fixture row: bare claude slot → `medium` | Change `"expectedEffort": "medium"` to `"expectedEffort": null` in ONE fixture row |
| Omit contract: gemini → null | Temporarily add `gemini` to `RUNTIMES_WITH_REASONING_EFFORT` in model-catalog.cjs |
| translateEffortForCodex: max → xhigh | Change `return effort === 'max' ? 'xhigh' : effort` to pass-through |
| Haiku → null (no medium floor) | Remove the haiku guard at core.cjs:1663 |
| Parser: colon provider ID → effort null | Change `lastIndexOf(';')` to `indexOf(';')` |

These mutations are documented per test in the executor's SUMMARY — not committed.

**Antipattern guard form:**
The guard is a test within `feat-58-regression.test.cjs` that reads all `tests/*.cjs` files and checks:

1. **`indexOf`-as-boolean false-pass:** regex `\.indexOf\s*\(.*\)\s*[^!=><!]` (a `indexOf()` result used without `!== -1` or `> -1` check). The canonical false-pass: `assert.ok(str.indexOf('medium'))` passes when the substring is at index 0 only fails for truthiness test — stricter check: flag any `assert.ok(.*\.indexOf(` pattern.

2. **`medium`/`high` substring collision:** any `\.includes\s*\(\s*['"](?:medium|high)['"]` inside an assert call — these can pass when the string is `"xhigh"` (contains "high") or when `"medium"` is a prefix of something. Correct assertion is `assert.strictEqual(effort, 'medium')`.

**Existing collisions in current suite to catch:** The current test suite uses `assert.ok(toml.includes('model_reasoning_effort = "xhigh"'))` in `feat-57-install-translation.test.cjs` line 189-191 — this is safe because it matches the full key-value pair. The guard should be scoped to effort-value assertions specifically: flag `assert.ok(.*\.includes\(['"](?:medium|high|xhigh|max|low)['"])` patterns where the match is just the token not a full structured line. The planner should refine the exact regex.

## Common Pitfalls

### Pitfall 1: Dynamic golden computing expected FROM the resolver
**What goes wrong:** Computing expected values in the test from `_resolveAgentSlot` + `parseModelEffort` — exactly what feat-53 does. A resolver that drifts wrong-but-consistently will still match.
**How to avoid:** Golden fixture values must be LITERAL strings written to JSON, not derived at test time from the live resolver.
**Warning signs:** Any test that calls `_resolveAgentSlot` to compute the "expected" value is a dynamic golden, not a static one.

### Pitfall 2: Fixture row count explosion
**What goes wrong:** Adding all 33 agents × 5 profiles × 15 runtimes = 2475 rows including nulls for non-effort runtimes.
**How to avoid:** D-02 is explicit — omit contract is ONE row per non-effort runtime, not 33×profiles. Keep effort-relevant rows to 33×4×2 = 264 rows (quality/balanced/budget/inherit × claude/codex).

### Pitfall 3: Forgetting the `adaptive` profile
**What goes wrong:** `MODEL_PROFILES` has 4 non-inherit named profiles: quality, balanced, budget, adaptive. feat-53 uses only 3+inherit. Adaptive uses `adaptiveTierMap` which maps agents to their `routingTier` slot. The adaptive slot for most agents is a bare tier alias (no `;effort`) so it hits the D-08 medium floor — but this needs confirming against the actual catalog values.
**How to avoid:** The regeneration script should include `adaptive` in the matrix; the planner decides whether to include it in the committed fixture per D-02 scope.

### Pitfall 4: `haiku` in golden rows for non-haiku agents
**What goes wrong:** Assuming all agents on `budget` profile are haiku. Some agents (gsd-planner, gsd-executor, gsd-code-fixer, etc.) have `budget: "sonnet;medium"` in their catalog entry — they are NOT haiku on budget.
**How to avoid:** Read from `MODEL_PROFILES[agent][profile]` directly (or via regeneration script). Confirmed from live catalog: only certain agents map to `haiku` on budget. The regeneration script handles this automatically.

### Pitfall 5: `indexOf`-as-boolean antipattern guard too broad
**What goes wrong:** The guard regex fires on legitimate uses of `.indexOf` for structural/non-effort purposes.
**How to avoid:** Scope the guard to effort-value assertions only: scan for the pattern inside `assert.*` call sites and specifically for effort token strings (`low|medium|high|xhigh|max`).

### Antipattern guard skeleton
```javascript
describe('TEST-04: antipattern guard — no indexOf-as-boolean or medium/high substring collision', () => {
  const testFiles = fs.readdirSync(path.join(__dirname))
    .filter(f => f.endsWith('.test.cjs'));

  for (const file of testFiles) {
    test(`${file}: no indexOf-as-boolean on effort values`, () => {
      const src = fs.readFileSync(path.join(__dirname, file), 'utf-8');
      // Flag: assert.ok(someStr.indexOf('medium')) — indexOf result used as boolean
      const matches = src.match(/assert\.ok\([^)]*\.indexOf\s*\(\s*['"](?:low|medium|high|xhigh|max)['"]\s*\)/g);
      assert.strictEqual(matches, null, `${file}: indexOf-as-boolean false-pass detected: ${matches}`);
    });

    test(`${file}: no bare includes('medium'/'high') in assert.ok`, () => {
      const src = fs.readFileSync(path.join(__dirname, file), 'utf-8');
      // Flag: assert.ok(x.includes('medium')) or assert.ok(x.includes('high'))
      // where the match is just the token (collision risk: 'xhigh' contains 'high')
      const matches = src.match(/assert\.ok\([^)]*\.includes\s*\(\s*['"](?:medium|high)['"]\s*\)[^)]*\)/g);
      assert.strictEqual(matches, null, `${file}: bare includes('medium'/'high') in assert.ok detected: ${matches}`);
    });
  }
});
```
