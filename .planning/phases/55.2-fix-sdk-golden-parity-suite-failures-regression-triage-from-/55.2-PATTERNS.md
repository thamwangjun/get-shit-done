## Orienting Insight (read first)

The CONTEXT frames `intel.update` and `verify.codebase-drift` as "missing native handlers."
The codebase shows the more precise truth the planner must resolve:

1. **`intelUpdate` already exists as a fully-correct SDK handler** at
   `sdk/src/query/intel.ts:394-404` — its output already byte-matches the CJS oracle
   `intelUpdate` (`get-shit-done/bin/lib/intel.cjs:315-322`). It is **dead code**: nothing
   imports it. The entire `intel.*` family is **intentionally NOT registered** in the SDK
   registry (`command-static-catalog-domain.ts:16-20`, `command-manifest.non-family.ts:74-76`)
   because intel dispatches CJS-only via `gsd-tools.cjs case 'intel':`.
2. **`verify.codebase-drift` is intentionally omitted** from both the verify family handler
   map (`handlers/verify/index.ts:16-17`) and the verify manifest
   (`command-manifest.verify.ts:16-18`), documented as out-of-seam / CJS-only per ADR 3524.

So the golden tests at `golden.integration.test.ts:881` (`intel.update`) and `:943`
(`verify.codebase-drift`) call `registry.dispatch('intel.update'|'verify.codebase-drift', ...)`,
which throws `Unknown command ... No native handler registered` (`registry.ts:121-122`).

Two coherent resolutions exist, and **D-204 makes "register the handler" the default**:
- **(A) Register** the handlers so dispatch succeeds and parity holds — adds them to the SDK
  seam, reversing the phase-55 ADR-3524 omission.
- **(B) Exception** — add them to the golden coverage exception path
  (`golden-policy.ts NO_CJS_SUBPROCESS_REASON`) AND remove the integration-test `describe`
  blocks / the `intel.update` allowlist entry, keeping them CJS-only.

The planner must pick per D-204 (register by default; exception only with recorded rationale).
The patterns below give concrete analogs for **both** paths.

## Pattern Assignments

### `intel.update` native handler — analog: `intelStatus` / `intelUpdate` (already written)

**Analog file:** `sdk/src/query/intel.ts`

**The handler already exists and matches the CJS oracle** (`intel.ts:394-404`):
```typescript
export const intelUpdate: QueryHandler = async (_args, projectDir, _workstream) => {
  if (!isIntelEnabled(projectDir)) {
    return { data: { disabled: true, message: INTEL_DISABLED_MSG } };
  }
  return {
    data: {
      action: 'spawn_agent',
      message: 'Run gsd-tools intel update or spawn gsd-intel-updater agent for full refresh',
    },
  };
};
```

**CJS oracle it must match** (`get-shit-done/bin/lib/intel.cjs:315-322`):
```javascript
function intelUpdate(planningDir) {
  if (!isIntelEnabled(planningDir)) return disabledResponse();
  return {
    action: 'spawn_agent',
    message: 'Run gsd-tools intel update or spawn gsd-intel-updater agent for full refresh'
  };
}
```
These are byte-identical in shape — so if `intel.update` is registered (path A), the golden
test should pass with no handler-body changes. The work is **registration**, not authoring.

**Registration analog — how a registered command's handler reaches the registry.** Intel is a
**non-family** static-catalog command. The intel handlers were deliberately removed from the
domain static catalog; the comment marks the exact insertion site:

`sdk/src/query/command-static-catalog-domain.ts:16-20` (import-site marker) and `:94-95`
(entry-site marker):
```typescript
// intel.* handlers intentionally NOT imported — intel (bin/lib/intel.cjs) is
// ... dispatched by the `case 'intel':` branch in get-shit-done/bin/gsd-tools.cjs ...
  // intel.* entries removed — see import-section comment above. Intel verbs
  // dispatch via bin/gsd-tools.cjs `case 'intel':` direct to bin/lib/intel.cjs.
```
To register (path A): import `intelUpdate` here and add a static-catalog entry
`{ canonical: 'intel.update', handler: intelUpdate, ... }` mirroring sibling static entries in
`command-static-catalog-domain.ts`. Compare a registered non-family read row pattern in
`command-manifest.non-family.ts` for the manifest shape.

### `verify.codebase-drift` native handler — analog: `verifySchemaDrift`

**Analog file (handler body):** `sdk/src/query/verify.ts` → `verifySchemaDrift`
(imported at `handlers/verify/index.ts:4`). `verify.schema-drift` is the closest analog by
role (verify family) AND data flow (drift detection, request-response JSON).

**Registration analog — family handler map** (`sdk/src/handlers/verify/index.ts:8-18`):
```typescript
export const VERIFY_FAMILY_HANDLERS: Readonly<Record<string, QueryHandler>> = {
  'verify.plan-structure': verifyPlanStructure,
  ...
  'verify.schema-drift': verifySchemaDrift,
  // 'verify.codebase-drift' intentionally omitted — out-of-seam CJS-only
  // per ADR/PRD 3524 §3 / L160. Router dispatches direct to CJS handler.

```
Path A: add `verifyCodebaseDrift` import + `'verify.codebase-drift': verifyCodebaseDrift,`
here, mirroring the schema-drift line, and remove the "intentionally omitted" comment.

**Registration analog — command manifest** (`sdk/src/query/command-manifest.verify.ts:13-18`):
```typescript
{ family: 'verify', canonical: 'verify.schema-drift', aliases: ['verify schema-drift'], mutation: false, outputMode: 'json' },
// verify.codebase-drift intentionally NOT in this manifest — drift is
// out-of-seam (CJS-only) per ADR/PRD 3524 §3 / L160. ...
```
Path A: add a `verify.codebase-drift` row mirroring the schema-drift row. The manifest →
`COMMAND_DEFINITIONS_BY_FAMILY` → `buildAliasGroup('verify')`
(`registry-assembly-descriptor.ts:28-44`) chain then wires `canonical → handler` automatically,
provided the `handler_key` in the command definition matches the family-handler map key.

**CJS oracle:** `get-shit-done/bin/lib/drift.cjs` (the `verify codebase-drift` branch in
`gsd-tools.cjs`). New handler output must `toEqual` this oracle (D-203).

### How dispatch reaches a handler (shared registration mechanics)

`createRegistry()` (`registry-assembly.ts:71-78`) → `buildRegistry()` walks
`REGISTRY_ASSEMBLY_PLAN` (`registry-assembly-descriptor.ts:73-87`), running each `static`
group via `registerStaticCatalog` and each `alias` family via `registerAliasCatalog`
(`registry-assembly.ts:42-53`). Family handlers come from `FAMILY_HANDLERS`
(`command-family-handlers.ts:11-19`); non-family commands (intel, audit, etc.) come from the
static catalogs. **`getHandler` returns `undefined` and `dispatch` throws** when unregistered
(`registry.ts:104, 118-122`).

export function nativeFailureError(input: { message: string; command: string; args: string[]; }): QueryDispatchError {

The `native_failure` kind is consumed in `sdk/src/runtime-bridge-sync/index.ts:64` and

`query-error-taxonomy.test.ts`, `query-dispatch.test.ts`, `runtime-bridge-sync/index.test.ts`.
**Apply:** once `intel.update`/`verify.codebase-drift` register, dispatch no longer throws
`Unknown command`, so any test expecting them to classify as `native_failure` for an
*unregistered* command must be reconciled — confirm whether the failing meta test expects
"registered + parity" (path A) or "classified as native_failure because CJS-only" (path B).

### JSON-parity divergence fixes (cause-c handlers)

For the cluster `intel.status/diff/validate/query/extract-exports`, `history.digest`,
`phase-plan-index`, `init.quick/todos/manager/map-codebase`, `audit-open`, `validate.health`:

**Pattern:** each is already a registered (or parity-rowed) handler whose output drifted from
its CJS oracle. The fix is per-handler: read the SDK handler, read the matching `bin/lib/*.cjs`
function, diff the JSON shape, fix the SDK side to match (D-203 — CJS canonical). The parity
rows live in `sdk/src/golden/read-only-golden-rows.ts:20-` (e.g. `intel.status` row line 35,
`intel.extract-exports` lines 39-44, `verify.schema-drift` line 51). The test harness is
`read-only-parity.integration.test.ts:26-28`:
```typescript
const gsdOutput = await captureGsdToolsOutput(row.cjs, row.cjsArgs, REPO_ROOT);
const registry = createRegistry();
const sdkResult = await registry.dispatch(row.canonical, row.sdkArgs, REPO_ROOT);
// then expect(sdkResult.data).toEqual(gsdOutput)
```
**Note (intel parity rows + non-registration tension):** rows 35-44 dispatch `intel.status`
etc. through `registry.dispatch`. If intel.* is currently unregistered, these rows themselves
throw — meaning intel parity fixes likely REQUIRE registering the intel family (path A) to even
run. The planner should treat "register intel.*" and "fix intel JSON divergence" as coupled.

**Volatile-key handling:** for `audit-open`, exclude `scanned_at` before `toEqual` (per CONTEXT
line 23). The repo already has normalize helpers for this pattern: see
`golden.integration.test.ts` use of `normalizeDocsInitPayload` / `omitAgentInstallFields`
(lines 866-873) and `omitInitExecutePhaseVolatile` (referenced in read-only-golden-rows.ts:67)
as the established volatile-stripping analog to copy.

### Golden coverage policy ("integration-covered or excepted")
**Source:** `sdk/src/golden/golden-policy.ts:103-120` (`verifyGoldenPolicyComplete`).
Every canonical from `getCanonicalRegistryCommands()`
(`registry-canonical-commands.ts:9-32`) must be in `GOLDEN_PARITY_INTEGRATION_COVERED`
(union of `golden-integration-covered.ts` + `readOnlyGoldenCanonicals()` +
`GOLDEN_MUTATION_SUBPROCESS_COVERED`, built at `golden-policy.ts:70-82`) OR have a
`GOLDEN_PARITY_EXCEPTIONS` rationale.
**Apply to:** any command added/removed from the registry in this phase.
- Path A (register): the canonical newly appears in `getCanonicalRegistryCommands()`, so it
  MUST be added to the integration-covered allowlist or an exception. `intel.update` is
  ALREADY in `golden-integration-covered.ts:21` — registering it makes that entry valid
  (currently it may be stale-flagged by `golden-policy.ts:113-119` if not in the registry).
- Path B (exception): add a `NO_CJS_SUBPROCESS_REASON` row mirroring `golden-policy.ts:25-62`
  with explicit rationale (D-204), and remove the integration `describe` + allowlist entry.

### Manifest → handler wiring (path A template, family commands)
**Source chain:** `command-manifest.verify.ts` → `command-definition.ts`
(`COMMAND_DEFINITIONS_BY_FAMILY`) → `registry-assembly-descriptor.ts:28-44` `buildAliasGroup`
matches `entry.handler_key` against the family handler map. A new family canonical needs:
manifest row + command-definition entry (with `handler_key`) + family-handler map entry. Trace
the `verify.schema-drift` end-to-end as the working reference.
