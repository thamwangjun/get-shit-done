### Introducing Surface — Named Suspects Attribution

Suspect-first investigation per D-202 (best-effort, not exhaustive bisect):

**Cluster A: Missing native handlers (2 tests)**

- `intel.update` and `verify.codebase-drift` throw `Unknown command … No native handler registered`
  at `registry.ts:121-122` on every `registry.dispatch()` call.
- Root: Both were **intentionally unregistered** in the upstream Phase 6 CJS↔SDK seam migration
  (`ae63cbe55` — *"feat(3575): Phase 6 — CJS↔SDK seam migration end-to-end complete"*, landed
  `2026-05-16`). `intel.*` was removed from `command-static-catalog-domain.ts` with an explicit
  "dispatched via `case 'intel':` in gsd-tools.cjs" comment. `verify.codebase-drift` was omitted
  from `handlers/verify/index.ts` and `command-manifest.verify.ts` with "out-of-seam / CJS-only
  per ADR 3524" comment.
- The golden integration tests that call `registry.dispatch('intel.update'|'verify.codebase-drift')`
  have always thrown since that upstream import — the tests were written against a registry state
  that no longer exists.
- **Phase-55 primary suspects `e4a841cd` / `abfcbf2b` do NOT touch the registry** — they only widen
  `AgentCatalogEntry` types and strip `;effort` in `resolveModelInternal`. These commits did not
  introduce or worsen this cluster.
- **Introducing surface: upstream `ae63cbe55` (Phase 6, pre-phase-54), inherited through phase 55.**

**Cluster B: intel.* JSON-parity (5 tests)**

- `intel.status/diff/validate/query/extract-exports` in `read-only-parity.integration.test.ts`
  fail with `Unknown command: "intel.*". No native handler registered.`
- Root: Same as Cluster A — `read-only-golden-rows.ts` dispatches via `registry.dispatch('intel.*')`
  which throws because the intel family is unregistered.
- `git log --oneline --all -- sdk/src/golden/read-only-golden-rows.ts` shows rows for `intel.status`
  and `intel.extract-exports` were present since `c5b144552` (original harness). The rows became
  broken when `ae63cbe55` removed the registry registration.
- **Introducing surface: upstream `ae63cbe55` (Phase 6, pre-phase-54), inherited through phase 55.**

**Cluster C: JSON-parity mismatches — init.* handlers (4 tests)**

- `init.quick`, `init.todos`, `init.manager`, `init.map-codebase` fail with JSON shape divergence
  (not "Unknown command").
- Root: Phase-54 commit `f0107ba64` (*"fix(54): IN-02 add golden parity rows for 12 newly ported
  init handlers"*, `2026-06-02 12:35`) added `READ_ONLY_JSON_PARITY_ROWS` entries for these
  handlers. The SDK handlers were not yet fully aligned with the CJS oracle at the time of
  row addition. Phase-55 commits `44c150b42` and `abfcbf2b` added `*_effort` siblings to the
  init builder outputs — these new fields appear in `gsd-tools.cjs` output but are absent or
  differently shaped in the SDK handlers, causing `toEqual` failures.
- **Primary introducing surface: `f0107ba64` (phase 54 IN-02) added the rows before SDK alignment;
  `44c150b42` / `abfcbf2b` (phase 55-01) widened the JSON divergence via effort sibling fields.**

**Cluster D: Other JSON-parity mismatches (3 tests)**

- `history.digest`, `phase-plan-index`, `audit-open` fail with JSON shape divergence.
- `history.digest` and `phase-plan-index` rows exist in `read-only-golden-rows.ts` since the
  original harness (`c5b144552`). `audit-open` has a dedicated describe block in the parity test.
- Root: SDK handler output drifted from `gsd-tools.cjs` — likely during phase-54/55 init and
  effort work that modified shared builder paths. Precise diff requires Wave 2 investigation
  per handler.
- **Introducing surface: phase-54 IN-02 / phase-55-01 effort sibling work (same as Cluster C).**

**Cluster E: validate.health JSON mismatch (1 test)**

- `validate.health` in `golden.integration.test.ts` fails with JSON shape divergence.
- Root: SDK `validate.health` handler output diverged from CJS. Precise diff requires Wave 2
  investigation.
- **Introducing surface: phase-54 / phase-55 handler work (TBD — Wave 2 will diff the shapes).**

**Cluster F: Meta/policy (2 tests)**

- `executeForCjs > native_failure classification` fails: `expected true to be false` — a test
  asserting that a registered handler does NOT succeed when expected to fail via native_failure
  path. This is likely a consequence of Cluster A: with `intel.update` / `verify.codebase-drift`
  unregistered, the `native_failure` classification path test exercises an unexpected code branch.
- `golden policy > every canonical registry command is integration-covered or excepted` fails
  with `Error: Stale GOLDEN_PARITY_INTEGRATION_COVERED` — `golden-policy.ts` detects that
  `intel.update` appears in `golden-integration-covered.ts` allowlist but is NOT in the registry
  (because it was unregistered). The allowlist entry is stale.
- **Introducing surface: upstream `ae63cbe55` (Phase 6) — same root as Clusters A and B.**

## Parity Oracle Policy (D-203)

`gsd-tools.cjs` is the canonical reference oracle for CLI↔SDK parity. On any divergence between
SDK handler output and `gsd-tools.cjs` output:

1. Fix the SDK handler to match `gsd-tools.cjs`. Do NOT relax the golden assertion.
2. Regenerate golden fixtures ONLY from confirmed-correct `gsd-tools.cjs` output (D-104).
3. Override this default ONLY with concrete evidence that `gsd-tools.cjs` itself regressed during
   phase 55 (in which case fix the CLI source and document the override here).
4. Stale golden fixtures are a fixable symptom; do not treat them as evidence of CLI regression.

**No CLI regression evidence found in this investigation.** All 17 failures are attributable to
SDK-side gaps (missing registration, stale golden rows, JSON divergence) — not to `gsd-tools.cjs`
changes.

## Plan 02 Outcome (D-204 Registration Complete)

**Completed:** 2026-06-03

### verify.codebase-drift — cause and resolution

- **Cause:** `missing-handler` — intentionally omitted from `handlers/verify/index.ts` and
  `command-manifest.verify.ts` per ADR-3524. A prior Phase 6 stub used `execFileSync` back to
  `gsd-tools`, creating infinite SDK→CLI→SDK recursion.
- **D-204 choice:** Path A (register). The solution is a native TypeScript port of
  `cmdVerifyCodebaseDrift` (from `verify.cjs:1331-1459`) and the drift detection logic from
  `drift.cjs` (`detectDrift`, `readMappedCommit`, `chooseAffectedPaths`, etc.) — no subprocess
  call. This avoids the recursion entirely while matching the CJS oracle output.
- **Result:** `verify.codebase-drift` golden test passes unrelaxed. Handler registered in
  `VERIFY_FAMILY_HANDLERS` and manifest.

### intel.update (and intel.* family) — cause and resolution

- **Cause:** `missing-handler` — intel.* family was intentionally removed from
  `command-static-catalog-domain.ts` in upstream Phase 6 commit `ae63cbe55` (ADR-3524 §3).
  The `intelUpdate` handler body at `intel.ts:394-404` was dead code; nothing imported it.
- **D-204 choice:** Path A (register). All 8 intel handlers (`intelStatus`, `intelDiff`,
  `intelSnapshot`, `intelValidate`, `intelQuery`, `intelExtractExports`, `intelPatchMeta`,
  `intelUpdate`) imported and registered in `DOMAIN_STATIC_CATALOG`. Handler bodies required no
  changes — registration was the only missing step.
- **Result:** `intel.update` golden test passes unrelaxed. `intel.*` parity rows in
  `read-only-golden-rows.ts` now dispatch successfully (unblocking Plan 04 parity fixes).
  `golden-integration-covered.ts:21` allowlist entry `intel.update` is now valid.
  `golden-policy.ts` coverage gate passes (intel.snapshot + intel.patch-meta fall through to
  `MUTATION_DEFERRED_REASON`; all other intel.* canonicals covered by read-only rows or allowlist).
